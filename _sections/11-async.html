⑥ Async training and policy staleness

Async training is not a new loss. It is a scheduling choice: let rollout and training run at the same time instead of forcing the loop to wait at every phase boundary. The benefit is higher hardware utilization. The cost is policy lag: a sample may be generated by an older rollout actor than the actor state currently being optimized.

This section is about that cost. Async execution can create policy staleness, and RL infrastructure has to make that staleness visible and controlled. The useful way to read real systems is in three layers: first, which scheduling knobs create or limit overlap; second, how the framework records which policy version produced a sample or token; third, what happens to stale data once it reaches the trainer.

Policy staleness.

Call the trainer's current policy version v_current. If a sample was generated when the rollout engine was at version v_sample, its staleness is roughly v_current - v_sample. A staleness of zero is the clean on-policy case. Larger values mean the trainer is updating on data produced by older weights.

Layer 1: scheduling creates the lag

In a synchronous loop, the order is strict: generate batch i, train on batch i, sync weights, then generate batch i + 1. Async breaks that order. Miles' async entry point starts generation for the next rollout before training the current rollout batch:

Miles: train_async.py· launch the next rollout before training the current one 
# initial async rollout
rollout_data_next_future = rollout_manager.generate.remote(args.start_rollout_id)

for rollout_id in range(args.start_rollout_id, args.num_rollout):
    if rollout_data_next_future is not None:
        rollout_data_curr_ref = await rollout_data_next_future

    # Start the next rollout early.
    if rollout_id + 1 < args.num_rollout:
        rollout_data_next_future = rollout_manager.generate.remote(rollout_id + 1)

    if args.use_critic:
        critic_task = await eager_create_task(
            critic_model.train(rollout_id, rollout_data_curr_ref)
        )
        if rollout_id >= args.num_critic_only_steps:
            await actor_model.train(rollout_id, rollout_data_curr_ref)
        await critic_task
    else:
        await actor_model.train(rollout_id, rollout_data_curr_ref)

The overlap is visible in the order of the highlighted lines. generate.remote(...) launches rollout work and gives the driver a future-like handle instead of the finished batch. At the top of each loop, await rollout_data_next_future collects the batch that was launched earlier and makes it the current training batch. Then, before actor_model.train(...) starts, the driver launches generate.remote(rollout_id + 1) for the next batch. So while the actor is training on batch i, the rollout side may already be producing batch i + 1 with the rollout weights it currently has.

That is the concrete code path behind staleness. The training actor and rollout actor are separate states: actor_model.train(...) updates the training actor first, while the rollout actor changes only after a later weight-sync call. If training changes the actor from θ_t to θ_{t+1}, the already-launched rollout for batch i + 1 does not automatically restart under θ_{t+1}. The sample is stale when the trainer later consumes it under a newer policy version than the one that generated it.

The second scheduling knob is how often rollout weights are refreshed. Miles exposes this as update_weights_interval. Before syncing, it waits for any in-flight generation to finish, so the system does not mutate rollout weights in the middle of one generation call:

Miles: train_async.py· async weight-sync interval 
if (rollout_id + 1) % args.update_weights_interval == 0:
    # sync generate before update weights to prevent update weight in the middle of generation
    rollout_data_curr_ref = (
        await x
    ) if (x := rollout_data_next_future) is not None else None
    rollout_data_next_future = None
    await actor_model.update_weights()

If update_weights_interval = 1, rollout is refreshed after every training step. If the interval is larger, rollout can keep generating from older weights for longer. This knob does not correct off-policy data by itself. It controls how much policy lag the system is willing to create.

Layer 2: version accounting makes the lag visible

Once async can create stale samples, the framework needs a way to identify them. Miles records rollout weight versions on each Sample. This matters especially for multi-turn or partial rollouts, where one trajectory may involve several generation calls and therefore several rollout weight versions:

Miles: miles/utils/types.py· samples carry rollout weight versions 
@dataclass
class Sample:
    ...
    weight_versions: list[str] = field(default_factory=list)
    rollout_log_probs: list[float] | None = None

    @property
    def oldest_weight_version(self) -> int | None:
        numeric = [int(v) for v in self.weight_versions if str(v).isdigit()]
        return min(numeric) if numeric else None

    def update_from_meta_info(self, args, meta_info: dict):
        ...
        if "weight_version" in meta_info:
            self.weight_versions.append(meta_info["weight_version"])

The conservative choice is oldest_weight_version. If a trajectory contains versions [3, 3, 4], the oldest version is 3. That gives the staleness filter a safe answer to the question: how old is the oldest policy state used anywhere in this training example?

AReaL makes the same idea token-level. Its rollout workflow can return a versions tensor, where prompt tokens use -1 and generated tokens carry the policy version that produced them:

AReaL: areal/workflow/vision_rlvr.py· per-token rollout versions 
seq = resp.input_tokens + resp.output_tokens
logprobs = [0.0] * resp.input_len + resp.output_logprobs
loss_mask = [0] * resp.input_len + [1] * resp.output_len
versions = [-1] * resp.input_len + resp.output_versions

return {
    "input_ids": torch.tensor(seq, dtype=torch.long).unsqueeze(0),
    "loss_mask": torch.tensor(loss_mask, dtype=torch.int32).unsqueeze(0),
    "logprobs": torch.tensor(logprobs, dtype=torch.float32).unsqueeze(0),
    "versions": torch.tensor(versions, dtype=torch.int32).unsqueeze(0),
    "rewards": torch.tensor(reward, dtype=torch.float32).unsqueeze(0),
}

This is the same accounting idea at a finer granularity. Instead of saying "this sample came from version 3," AReaL can say "these generated token positions came from these versions." That becomes important when partial rollout or multi-turn generation crosses a weight update boundary.

Layer 3: stale data is filtered, bounded, or corrected

The simplest response is filtering. In Miles' fully async example, the rollout worker queries the current engine version, computes current_engine_version - oldest, and recycles a group if the gap exceeds max_weight_staleness:

Miles: examples/fully_async/fully_async_rollout.py· recycle rollout groups that are too stale 
def group_oldest_weight_version(group: list[Sample]) -> int | None:
    versions = [
        s.oldest_weight_version
        for s in group
        if s.oldest_weight_version is not None
    ]
    return min(versions) if versions else None

use_staleness_filter = getattr(args, "max_weight_staleness", None) is not None
if use_staleness_filter:
    current_engine_version = await _cached_version.get(args)

oldest = group_oldest_weight_version(group)
if oldest is not None and current_engine_version is not None:
    staleness = current_engine_version - oldest
    staleness_values.append(staleness)
    if staleness > args.max_weight_staleness:
        for s in group:
            s.reset_for_retry()
        data_buffer.add_samples([group])
        stale_groups_recycled += 1
        continue

This code is an admission rule for training data. Groups inside the allowed window enter the trainer. Groups outside the window are reset and put back into the data buffer. In other words, Miles turns "off-policy" from a vague warning into a version gap that can be measured and capped.

AReaL uses a related bound before too much work enters the system. Its async guide exposes max_head_offpolicyness: setting it to zero gives synchronous RL; setting it above zero allows rollout to get ahead by a bounded number of versions. The capacity manager uses that bound when deciding how many new rollouts can be pending or running:

AReaL: areal/infra/staleness_manager.py· staleness-aware rollout capacity 
def get_pending_limit(self) -> int:
    return (self.max_staleness + 1) * self.consumer_batch_size

def get_capacity(self) -> int:
    current_version = self.version_provider.get_version()
    concurrency_capacity = self.max_concurrent_rollouts - self.rollout_stat.running

    ofp = self.max_staleness
    sample_cnt = self.rollout_stat.accepted + self.rollout_stat.running
    consumer_bs = max(1, self.consumer_batch_size)
    staleness_capacity = (ofp + current_version + 1) * consumer_bs - sample_cnt

    return min(concurrency_capacity, staleness_capacity)

Miles filters completed groups by version gap; AReaL limits rollout capacity using a staleness bound. These are both operational controls. They reduce or cap how stale the accepted data can be.

Filtering and capacity limits answer one question: should this stale sample be allowed into training at all? Loss-level correction answers a different question: if we do train on it, should it count as much as an on-policy sample? To answer that, the trainer needs two log probabilities for the same generated tokens. The rollout-side logprob says how likely the old rollout policy was to produce the token. The training-side logprob says how likely the current actor is to produce that same token. Their ratio estimates how far the accepted sample has drifted from the policy now being optimized.

Correction ratio. For one generated token a_j with context h_j, the two log probabilities are:

rollout logprob = log πrollout(aj | hj)
training logprob = log πcurrent(aj | hj)

The importance ratio compares the current actor with the policy that generated the token:

ρj = exp(log πcurrent(aj | hj) - log πrollout(aj | hj))

Truncated importance sampling clips that ratio before it enters the policy-gradient term:

ρ̂j = clip(ρj, 1 - ε, 1 + ε)

If the sample is perfectly on-policy, the rollout policy and current policy are the same, so ρ_j should be close to 1. If async scheduling lets rollout lag behind training, π_rollout may be older than π_current. The ratio tells the loss how much the current actor's probability differs from the actor that actually generated the token.

Miles treats this as part of its broader train/inference mismatch correction path. The rollout-correction guide describes TIS/MIS as algorithmic rollout correction, and compute_mis_weights is where the log-ratio above becomes bounded importance weights. Async staleness is one possible source of this mismatch; different engines, precision modes, or inference settings can create the same need. The clean mental model is:

  • Scheduling knobs create or limit overlap: queue size, rollout concurrency, weight-sync interval.
  • Version accounting records which policy produced each sample or token.
  • Filtering and bounds decide which stale samples are allowed into training.
  • Loss correction can reweight accepted off-policy samples when the needed logprob evidence is available.
