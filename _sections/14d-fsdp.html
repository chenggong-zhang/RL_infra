Case study — FSDP, the other training backbone

The training sections of this survey ran on Megatron-LM. But look at the landscape table: verl's default training backend is FSDP, and OpenRLHF, SkyRL, and AReaL reach for it too. This survey has used the name nine times without defining it. This case study closes that gap: what FSDP actually does, why RL frameworks pick it first, and where RL specifically presses on it. The code is verl's, which the previous case study already introduced.

FSDP stands for Fully Sharded Data Parallel. It is PyTorch's built-in implementation of an idea published as ZeRO (arxiv 1910.02054): keep data parallelism's simple mental model — every rank runs the whole model on its own slice of the batch — but stop paying data parallelism's memory price.

The idea: shard everything, gather just in time

Recall plain data parallelism from the Megatron section: several ranks hold the same logical replica, each processes different examples, and gradients are synchronized before the optimizer step. The memory cost is that every rank holds everything: the parameters, the gradients, and the optimizer states. For mixed-precision Adam training, that is roughly 16 bytes per parameter before a single activation is stored — the arithmetic from Primitive ②. A 70B model needs about 1.1 TB of state per replica. No single GPU holds that.

The observation behind ZeRO and FSDP: nothing requires all of that state to be resident at once. The optimizer states are only touched at the optimizer step. The gradients of layer 40 are not needed while layer 3 computes. Even the parameters of layer 40 are not needed while layer 3 runs forward. So shard all three kinds of state across the data-parallel ranks — each rank permanently owns 1/N of every layer — and materialize full parameters only for the layer that is currently executing:

plain DP:  every rank holds   full params + full grads + full optimizer states
FSDP:      every rank holds   1/N params  + 1/N grads  + 1/N optimizer states

forward, layer by layer:
  all-gather layer i's params  ->  run layer i  ->  free the gathered params
backward, layer by layer:
  all-gather layer i's params  ->  compute grads  ->  reduce-scatter grads  ->  free
optimizer step:
  each rank updates only the 1/N shard it owns

Two of the collective operations here are new names for familiar shapes. An all-gather collects the shards from all ranks so that each rank temporarily holds the full tensor. A reduce-scatter is the reverse composed with a sum: gradients are summed across ranks, and each rank keeps only the 1/N piece it owns. Peak memory per rank drops from "the whole model" to "my shard, plus one layer's worth of gathered parameters."

The price is communication volume. Plain DP moves each gradient once through an all-reduce, which costs about 2× the parameter volume per step. FSDP all-gathers parameters twice (forward and backward) and reduce-scatters gradients once, roughly 3× the parameter volume — about 1.5 times more traffic than plain DP, in exchange for an N-fold memory reduction. The bandwidth is affordable precisely because the gathers are per-layer and can be prefetched: while layer i computes, the parameters of layer i+1 are already in flight.

Why RL frameworks reach for it first

The deep difference from Megatron is not the sharding arithmetic. It is where the parallelism lives. Megatron's parallelism is intrusive: TP splits the inside of a layer, so the model must be written in Megatron's building blocks, and a HuggingFace checkpoint must be converted into Megatron's format before training (that is what Megatron-Bridge exists for). FSDP's parallelism is a wrapper: it takes an ordinary nn.Module, walks its submodules, and replaces their parameters with shards. The model code does not change. verl's FSDP engine shows this directly — module here is a plain HuggingFace transformer:

verl/workers/engine/fsdp/transformer_impl.py· wrapping a HuggingFace module 
module = FSDP(
    module,                                  # an ordinary HF nn.Module
    auto_wrap_policy=auto_wrap_policy,       # which submodules become shard units
    sharding_strategy=sharding_strategy,
    mixed_precision=mixed_precision,
    device_mesh=self.device_mesh,
    cpu_offload=cpu_offload,
)

This is why RL frameworks default to FSDP. RL post-training starts from a HuggingFace checkpoint — the SFT model someone just produced. With FSDP, that checkpoint loads directly and training starts; with Megatron, a conversion step and a Megatron-compatible model definition stand in between. For a research team iterating on algorithms with dense models in the 1B–100B range, FSDP is the shortest path from checkpoint to gradient.

The honest ceiling: FSDP shards along the data-parallel axis only. There is no pipeline stage, no expert parallelism, and in the basic story no tensor parallelism (FSDP2 can compose with TP through DTensor, but that is the frontier, not the default). For MoE giants like DeepSeek-V3, where expert parallelism and its routing invariants dominate the design, the Megatron path is the practical one — which is exactly why slime and Miles are Megatron-based while verl offers both and defaults to FSDP.

FSDP1, FSDP2, and DTensor

PyTorch has shipped two generations of the idea, and production RL code currently handles both. FSDP1 flattens all parameters of a shard unit into one FlatParameter buffer and shards that buffer — efficient, but the flattening makes individual parameters awkward to address, which matters when weight sync needs to iterate them by name. FSDP2 (the fully_shard API) shards each parameter separately as a DTensor — a tensor that knows its device mesh and placement, i.e., which ranks hold which slice of it. A DTensor can reconstruct its full value on demand: full_tensor() performs the all-gather and returns the assembled tensor. Keep that method in mind; it is the hinge of the next subsection.

verl supports both generations, and its utility file records the migration honestly — the same names import from three different places depending on the PyTorch version:

verl/utils/fsdp_utils.py· the FSDP2 import dance 
if version.parse(torch.__version__) >= version.parse("2.6"):
    from torch.distributed.fsdp import CPUOffloadPolicy, FSDPModule, MixedPrecisionPolicy, fully_shard
    from torch.distributed.tensor import DTensor, Shard
elif version.parse(torch.__version__) >= version.parse("2.4"):
    from torch.distributed._composable.fsdp import CPUOffloadPolicy, FSDPModule, MixedPrecisionPolicy, fully_shard

RL pressure point 1: materializing weights for rollout sync

After the optimizer step, the new policy has to reach the rollout engine — the trainer-side half of Primitive ③. Under FSDP, no rank holds a full parameter, so materializing the weights means all-gathering them, parameter by parameter. verl builds this as a generator over named parameters, calling full_tensor() on each shard and downcasting to BF16 to halve the sync traffic:

verl/workers/engine/fsdp/transformer_impl.py· per-tensor weight materialization 
per_tensor_param = (
    (
        name,
        param.to(device, non_blocking=True).full_tensor().to(torch.bfloat16, non_blocking=True)
        if isinstance(param, DTensor)
        else param,
    )
    for name, param in params.items()
)

This snippet finally explains an invariant that the verl case study could only state as a rule: every rank must walk this generator, even though only one rank sends the result to SGLang. Now the reason is visible. Each full_tensor() call is an all-gather — a collective operation in which every rank of the FSDP group must participate, because each rank holds a shard that the others need. If one rank skips the walk, the remaining ranks wait forever for its shard, and the sync deadlocks. The invariant is not a framework convention; it is the arithmetic of sharding.

RL pressure point 2: getting out of rollout's way

In a sleep-mode hybrid engine (Primitive ②), trainer and rollout engine time-share the same GPUs. During rollout, the trainer's memory — even the sharded 1/N — is dead weight that the inference engine needs for KV cache. verl's utilities move the FSDP shards and optimizer states to host memory and back around each phase: offload_fsdp_model_to_cpu() / load_fsdp_model_to_gpu() for parameters, offload_fsdp_optimizer() / load_fsdp_optimizer() for Adam states, with FSDP2 variants alongside.

One comment in the engine code is worth quoting because it shows how sharp the memory choreography is. verl forces CPU offload on for the reference policy and forces it off for the actor:

verl/workers/engine/fsdp/transformer_impl.py· offload: forced on for ref, forced off for actor 
# We force reference policy to use CPUOffload to save memory.
# We force turn off CPUOffload for actor because it causes incorrect results when using grad accumulation
cpu_offload = None
if self.engine_config.forward_only:
    cpu_offload = CPUOffload(offload_params=True)

The logic: the reference policy πref only ever runs forward (to supply the KL anchor), so its parameters can live on CPU and stream in per layer — slower, but it frees GPU memory for the actor. The actor cannot use the same trick, because FSDP1's automatic offload interacts incorrectly with gradient accumulation: gradients accumulated across microbatches must stay resident between backward passes. One flag, two opposite settings, both load-bearing.

The logprob recompute — Obligation 1 from the Megatron section — runs under this same machinery, as a forward-only pass over the rollout tokens: one all-gather sweep through the layers, no backward, no gradient memory. verl marks these engines with the same forward_only flag shown above.

Choosing between the backbones

QuestionFSDPMegatron
Starting from a HuggingFace checkpoint? Loads directly; the model code is unchanged Requires conversion (Megatron-Bridge) and a Megatron model definition
Parallelism dimensions Sharded DP only (FSDP2 + TP via DTensor is emerging) TP · PP · DP · EP · CP, freely composed
Dense models, ~1B–100B The comfortable default Works, with more setup than the problem needs
MoE at DeepSeek scale Out of reach — no expert parallelism Native EP, plus the routing-replay invariants RL needs
Who uses it in this survey verl (default), OpenRLHF, SkyRL, AReaL slime, Miles, verl (as an option), Megatron's own megatron/rl/

The two backbones are not competitors so much as two answers to "where should parallelism live": inside the model definition (Megatron — maximal control, maximal ceiling) or wrapped around it (FSDP — minimal friction, DP-shaped ceiling). The four obligations from the Megatron section apply to both unchanged; only the machinery underneath differs. That is the real lesson of verl's backend-switch design: recompute, loss, packing, and weight materialization are the stable interface, and the training backbone behind them is a config flag.
