Case study — FSDP, ZeRO, and HSDP: where training state lives

Large-model training has more GPU-resident state than the model weights alone. Every update also produces gradients and maintains optimizer state. Data parallelism normally replicates all three on every rank, even though different ranks process different examples. ZeRO and FSDP reduce that replication. Their variants differ in one concrete question: which training states remain replicated, which are sharded, and when must a sharded parameter be reconstructed for computation?

This question is especially visible in RL infrastructure. The actor must fit during training, but its updated weights must also be materialized for the rollout engine. A sharding strategy therefore changes both the training memory budget and the cost of crossing the train/rollout boundary.

Start with the objects that occupy training memory

Let P denote model parameters, G gradients, O optimizer state, and A activations saved for backward. These symbols refer to bytes, not parameter counts. Plain data parallelism gives each of N ranks a complete model replica:

Training-state ledger.

memory per rank in DDP ≈ P + G + O + Alocal

Alocal depends on the local microbatch, sequence lengths, checkpointing, and activation precision. ZeRO's stages primarily reorganize P, G, and O; they do not automatically divide activation memory by the data-parallel world size.

For a common mixed-precision Adam configuration, one parameter may correspond to 2 bytes of BF16 model weight, 2 bytes of gradient, a 4-byte FP32 master weight, and two 4-byte Adam moments. That gives roughly 16 bytes per parameter before activations and temporary communication buffers. The exact number changes with optimizer, precision, quantization, and offloading, so the useful habit is to keep the three state classes separate rather than memorize one constant.

The ZeRO ladder: shard one state class at a time

ZeRO is a family of data-parallel memory layouts. All ranks still run the same logical model on different data, and their gradients still have to represent one global update. Each stage removes another form of redundant training state.

StrategyParametersGradientsOptimizer statePersistent state per rank
DDP / ZeRO-0 replicated replicated replicated P + G + O
ZeRO-1 replicated replicated sharded P + G + O/N
ZeRO-2 replicated sharded sharded P + (G + O)/N
ZeRO-3 / full sharding sharded outside computation sharded sharded (P + G + O)/N plus temporary gathered parameters

ZeRO-1 assigns each rank a subset of parameters to update. Every rank still has the full parameters and full reduced gradients, but it only keeps the optimizer state for its assigned subset. After those owners apply their optimizer updates, the new parameter values must be made consistent across replicas.

ZeRO-2 also partitions the reduced gradients. A reduce-scatter can sum gradients across data-parallel ranks and leave each rank with only the gradient shard corresponding to the optimizer state it owns. Full model parameters remain available on every rank, so forward and backward do not need just-in-time parameter all-gathers.

ZeRO-3 partitions the parameters as well. A rank normally holds only its parameter shards. Before a layer can run, the ranks that collectively own that layer exchange shards and reconstruct its full parameters. Those temporary full parameters can be released after use.

An eight-rank example. Using the illustrative 16-byte mixed-precision Adam ledger above, DDP stores about 16 bytes of persistent training state per parameter on every rank. ZeRO-1 reduces this to 2 + 2 + 12/8 = 5.5 bytes; ZeRO-2 to 2 + (2 + 12)/8 = 3.75 bytes; and ZeRO-3 to about 16/8 = 2 bytes. ZeRO-3 still needs temporary memory for the FSDP unit currently being computed, communication buffers, and activations.

How full sharding executes one Transformer layer

PyTorch's Fully Sharded Data Parallel implementation is closest to ZeRO-3 when it uses FULL_SHARD, or when an FSDP2 unit uses reshard_after_forward=True. Suppose four ranks own four shards of a layer's weight W:

Persistent state. Rank j begins with parameter shard Wj and the matching optimizer-state shard Oj. The four ranks collectively own one logical weight W; none of them needs to keep the complete weight between computations.

Forward and reshard. The parameter all-gather gives every rank a temporary full W. The parameters are now identical, but the activations are not: rank j runs the layer on its own local microbatch Xj. Under full sharding, the temporary full weight is released after forward, leaving each rank with its original shard again.

Backward. Computing input and parameter gradients requires the layer weights, so the ranks all-gather W a second time. Each rank's local examples produce a full gradient contribution dW(j). These four tensors differ because the ranks processed different data.

Reduce-scatter and optimizer step. Reduce-scatter sums the local gradient contributions and partitions the result. Rank j receives only the slice aligned with Wj:

gj = shardj(dW(0) + dW(1) + dW(2) + dW(3))

The local optimizer can now update Wj from gj and Oj. After every rank updates its own slice, their four new shards together form the next logical model weight.

Two collectives. all-gather starts with a different shard on each participating rank and gives every rank the concatenated tensor. reduce-scatter combines gradient contributions, normally by summing them, and then leaves each rank with a different shard of the result. The first operation temporarily reconstructs parameters; the second produces the sharded gradient that the local optimizer shard consumes.

The sharding strategy and the wrapping policy control two different parts of memory. Sharding determines how much parameter memory a rank keeps between computations, usually about P/N. The wrapping policy divides the model into FSDP units and therefore determines how many parameters are temporarily reconstructed by one all-gather. Before a unit runs, FSDP gathers the complete parameters for that unit; after the unit no longer needs them, those complete parameters can be released while the persistent shards remain.

A concrete memory count. Suppose a 24-block Transformer has 1 GB of parameters per block, so P = 24 GB, and it is fully sharded over eight ranks. Each rank permanently stores about P/N = 3 GB of parameter shards.

If the whole model is one FSDP unit, the first all-gather reconstructs all 24 GB on every rank. Parameter memory during computation is then roughly 3 GB of persistent shards + 24 GB of temporary full parameters. The model is sharded while idle, but most of that saving disappears while it runs.

If each Transformer block is one unit, a rank reconstructs only the current 1 GB block. When that block finishes, its full parameters are released and the next block is gathered. Parameter memory is now roughly 3 GB of persistent shards + 1 GB for the current full block.

Making units extremely small is not free. If every weight tensor is gathered separately, one Transformer block may trigger many small collective calls. Each collective has setup and synchronization overhead, so thousands of tiny gathers can be slower than a smaller number of well-sized gathers. One Transformer block is a common compromise: small enough to limit temporary parameter memory, but large enough to batch several tensors into one collective.

Prefetching changes the peak slightly. While block i is computing, FSDP may begin gathering block i + 1 so communication overlaps with computation. For a short interval, both units occupy memory. Ignoring activations and other buffers, peak parameter memory is therefore closer to:

P/N + Ucurrent + Uprefetch

Here U is the full parameter size of one FSDP unit. The central distinction is: sharding controls the persistent P/N term; wrapping controls the temporary U terms.

The two temporary terms above, Ucurrent and Uprefetch, are determined by where the framework places its fully_shard() boundaries. verl's FSDP2 setup shows that choice directly. It first identifies the Transformer blocks that should become separate FSDP units. Calling fully_shard(module) on one selected block assigns that block's parameters to one gather group. Only after all selected blocks have been assigned does verl call fully_shard(model) on the root model:

verl/utils/fsdp_utils.py· FSDP2 units are created bottom-up 
modules = _select_fsdp2_wrap_targets(
    model,
    fsdp_transformer_layer_cls_to_wrap,
)

for module in modules:
    fully_shard(module, **fsdp_kwargs)

fully_shard(model, **fsdp_kwargs)

The loop assigns each selected Transformer block to its own FSDP unit. When block i is about to run, FSDP gathers the parameters of block i; parameters belonging to the other blocks remain sharded. The final fully_shard(model) call handles parameters that were not assigned by the loop, such as token embeddings or the output projection. It does not absorb the already assigned Transformer blocks into one whole-model gather.

All of these units normally use the same device mesh, so the same FSDP ranks participate each time. The payload changes: one collective carries block 0's parameters, the next carries block 1's parameters, and so on. In the 24-block example above, if each selected module contains one 1 GB block, then Ucurrent = 1 GB. Grouping four blocks into one unit would instead make each gather, and the corresponding temporary full-parameter buffer, about 4 GB.

The ZeRO-2-style choice: keep parameters between forward and backward

Full sharding saves the most parameter memory, but it may communicate the same layer parameters twice in one training iteration: once before forward and again before backward. If the full parameters can remain in memory between those two computations, the second all-gather can be avoided.

The upper path minimizes parameter residency between the two passes. Its cost is the second all-gather before backward. The lower path keeps the full unit in memory across that interval, so backward can reuse it without another parameter collective. Both paths reduce-scatter gradients after backward and return to sharded parameters and sharded gradients for the local optimizer step.

FSDP1 calls this strategy SHARD_GRAD_OP. It is commonly described as ZeRO-2-style because gradients and optimizer states are sharded while parameters remain full through the forward/backward computation window. There is a small implementation distinction from canonical DeepSpeed ZeRO-2: FSDP may still store parameters as shards outside that window, whereas classic ZeRO-2 keeps model parameters replicated persistently. The relevant tradeoff is the same. Keeping full parameters longer uses more peak memory and removes a pre-backward all-gather.

verl exposes this choice as self.engine_config.reshard_after_forward. The first step is in the engine builder, before the strategy helper shown below. FSDP1 passes the value into get_sharding_strategy; FSDP2 places the same value directly in the keyword arguments later consumed by fully_shard():

verl/workers/engine/fsdp/transformer_impl.py· read the reshard configuration 
fsdp_mesh = self.device_mesh

# FSDP1: translate the boolean into a ShardingStrategy.
sharding_strategy = get_sharding_strategy(
    fsdp_mesh,
    zero3_enable=self.engine_config.reshard_after_forward,
)

if self.engine_config.strategy == "fsdp":
    module = FSDP(
        module,
        sharding_strategy=sharding_strategy,
        device_mesh=self.device_mesh,
        ...
    )

elif self.engine_config.strategy == "fsdp2":
    fsdp_kwargs = {
        "mesh": fsdp_mesh,
        "mp_policy": mp_policy,
        "offload_policy": offload_policy,
        "reshard_after_forward": self.engine_config.reshard_after_forward,
    }
    apply_fsdp2(module, fsdp_kwargs, self.engine_config)

The naming change in the FSDP1 path is easy to miss. The configuration is called reshard_after_forward, but the helper receives it under the local name zero3_enable. Inside that helper, True means the full-shard behavior associated with ZeRO-3, while False selects the ZeRO-2-style behavior. The helper also chooses the corresponding hybrid strategy when the device mesh is two-dimensional:

verl/workers/engine/fsdp/utils.py· full-shard and ZeRO-2-style strategies 
def get_sharding_strategy(device_mesh, zero3_enable=True):
    if zero3_enable:
        fsdp_strategy = ShardingStrategy.FULL_SHARD
        hsdp_strategy = ShardingStrategy.HYBRID_SHARD
    else:
        fsdp_strategy = ShardingStrategy.SHARD_GRAD_OP
        hsdp_strategy = ShardingStrategy._HYBRID_SHARD_ZERO2

    if device_mesh.ndim == 1:
        return fsdp_strategy
    elif device_mesh.ndim == 2:
        return hsdp_strategy

For a one-dimensional mesh, the complete chain is therefore:

engine_config.reshard_after_forward = True
  -> zero3_enable = True
  -> ShardingStrategy.FULL_SHARD
  -> release full parameters after forward and gather again before backward

engine_config.reshard_after_forward = False
  -> zero3_enable = False
  -> ShardingStrategy.SHARD_GRAD_OP
  -> retain full parameters through backward and avoid the second gather

FSDP2 does not perform this renaming. Its fsdp_kwargs passes reshard_after_forward into fully_shard() directly, using the same time-memory choice described in the PyTorch FSDP2 documentation.

HSDP: shard inside a group, replicate the group

Full sharding over every GPU minimizes persistent state per rank, but it also makes every parameter gather span the full sharding group. That becomes unattractive when a cluster has fast links within each node and slower links between nodes. Hybrid Sharded Data Parallel (HSDP) introduces two data-parallel dimensions:

  • A shard dimension jointly holds one model replica. Parameter all-gathers and gradient reduce-scatters occur inside this group.
  • A replicate dimension creates several copies of that sharded model. The replicas process different data and synchronize their corresponding gradient shards.

Consider 16 GPUs arranged as two nodes with eight GPUs each. Choose a shard-group size S=8 and a replica count R=2:

Persistent layout. One HSDP replica is the entire eight-GPU row, not one GPU. The eight ranks in node 0 collectively hold one logical model as W0 ... W7; node 1 holds a second copy with the same shard positions and processes different training data. Each GPU therefore stores roughly 1/8 of the persistent training state, not 1/16.

Parameter reconstruction. Before an FSDP unit runs, each row performs its own eight-rank all-gather. Every participating rank in node 0 reconstructs the full unit from node 0's shards, and node 1 does the same independently. When the shard groups are aligned with nodes, this high-volume parameter exchange can remain on the faster intra-node fabric.

Gradient synchronization. Backward first produces gradient contributions inside each replica. Reduce-scatter within a row sums those contributions and leaves the owner of position j with a reduced shard gj(r). The two owners at the same shard position then all-reduce across the replica dimension. After that second collective, both replicas have the same synchronized gj and will apply the same update to their copies of Wj.

HSDP therefore exchanges some memory efficiency for topology-aware communication. Full sharding over all 16 ranks would store about 1/16 of the state per GPU, but parameter all-gathers would span both nodes. HSDP stores 1/8 per GPU and keeps those parameter all-gathers inside each node; cross-node communication is applied to the already reduced gradient shards.

Do not confuse the two uses of "hybrid." A hybrid engine lets training and rollout time-share resources. HSDP is a training-state layout: it combines sharding and replication inside data parallelism. An RL system may use both at the same time, but they solve different problems.

In verl, world_size is the total number of training ranks, while fsdp_size is the number of ranks that shard one model replica. If fsdp_size equals world_size (or is -1), all ranks form one FSDP group. If it is a smaller divisor, verl creates a two-dimensional mesh of shape (world_size / fsdp_size, fsdp_size): the first dimension counts replicas, and the second counts shards within each replica.

verl/workers/engine/fsdp/utils.py· build the HSDP device mesh 
def create_device_mesh(world_size, fsdp_size):
    if fsdp_size < 0 or fsdp_size >= world_size:
        device_mesh = init_device_mesh(
            device_name,
            mesh_shape=(world_size,),
            mesh_dim_names=["fsdp"],
        )
    else:
        device_mesh = init_device_mesh(
            device_name,
            mesh_shape=(world_size // fsdp_size, fsdp_size),
            mesh_dim_names=["ddp", "fsdp"],
        )
    return device_mesh

With world_size=16 and fsdp_size=8, the mesh shape is (2, 8). Along the fsdp dimension, eight ranks shard one model replica. Along the dimension named ddp in this implementation, two corresponding shard owners are replicas. Because the mesh is two-dimensional, the strategy selector above returns HYBRID_SHARD rather than FULL_SHARD. This is the concrete code path from one integer configuration to HSDP's two sets of communication groups.

FSDP1 and FSDP2 represent the same idea differently

PyTorch now has two FSDP APIs. They perform similar collectives, but their parameter representations matter when framework code needs to inspect, save, offload, or export individual weights.

FSDP1FSDP2
Entry point FSDP(module, ...) wrapper fully_shard(module, ...) applied in place
Sharded representation parameters in a unit are commonly flattened into FlatParameter each original parameter remains a per-parameter DTensor
Parameter names flattening and wrapping make original parameters harder to address original fully qualified names are preserved
Placement description FSDP handles and process groups DeviceMesh plus placements such as Shard and Replicate
Full parameter access summon/full-state-dict APIs DTensor operations such as full_tensor()

DTensor matters here because FSDP2 changes what framework code sees when it asks for a parameter. FSDP1 hides sharding behind flattened internal buffers. FSDP2 keeps each named parameter visible, but represents it as a DTensor: one logical parameter whose local data is only the shard stored on the current rank.

For an ordinary training step, that representation can remain an implementation detail. It becomes visible at the train/rollout boundary. The rollout engine needs a complete named weight, while the trainer currently has a named DTensor shard. The DTensor remembers which mesh and placement produced that shard, so full_tensor() can gather the pieces and reconstruct the complete parameter. This is why verl's get_per_tensor_param() function in the next subsection checks isinstance(param, DTensor) and calls full_tensor() before handing each updated actor weight to the rollout side.

What RL adds to the FSDP lifecycle

In an ordinary FSDP training loop, parameter shards can remain inside the training runtime from one optimizer step to the next. RL post-training adds two phase boundaries. First, the policy updated by the trainer must become the policy used by the rollout engine. Second, when trainer and rollout share GPUs, the inactive training state may have to leave GPU memory so generation has room for serving weights and KV cache. The next two subsections follow these two boundaries separately.

1. Exporting a sharded actor to rollout

After the optimizer step, the new actor exists collectively across the FSDP ranks: rank j holds the updated shard Wj, but no rank necessarily holds the complete parameter W. Before the rollout engine can load the new actor, the trainer side has to recover complete named parameters:

This subsection focuses on the highlighted left-hand boundary. verl implements it lazily over the state dictionary; the FSDP2 branch calls full_tensor():

verl/workers/engine/fsdp/transformer_impl.py· materialize updated actor parameters 
params = self.module.state_dict()
device = get_device_id()

per_tensor_param = (
    (
        name,
        param.to(device, non_blocking=True).full_tensor()
        .to(torch.bfloat16, non_blocking=True)
        if isinstance(param, DTensor)
        else param,
    )
    for name, param in params.items()
)

The generator handles one named parameter at a time instead of first assembling a second full model. For a DTensor parameter, param.to(device) makes the local shard available on the accelerator if it was offloaded, and full_tensor() all-gathers the shards into the complete parameter. The final BF16 conversion reduces the representation passed downstream, although verl's nearby comment notes that some parameters, such as an MoE gate, may eventually need more selective precision control.

The generator is lazy, but the collective is not optional. When the downstream rollout adapter asks for the next tensor, all ranks participating in that DTensor operation must reach the corresponding full_tensor() call. The ranks along the shard dimension own different pieces of the answer. If one participant skips that parameter or traverses parameters in a different order, the others can wait for a collective that never completes.

verl decides whether to gather by checking the parameter representation: a DTensor is sharded, so it calls full_tensor(). OpenRLHF's DeepSpeed backend makes the same decision from the configured ZeRO stage. ZeRO-1 and ZeRO-2 leave parameters replicated; ZeRO-3 shards them, so only ZeRO-3 enables GatheredParameters:

openrlhf/trainer/ray/ppo_actor.py· ZeRO stage changes weight materialization 
def _gather_params_ctx(param):
    if self.strategy.args.ds.tensor_parallel_size > 1:
        return GatherReplacedLayerParams([param], model, enabled=True)

    return deepspeed.zero.GatheredParameters(
        [param],
        enabled=self.strategy.args.ds.zero_stage == 3,
    )

for name, param in params_to_sync:
    with _gather_params_ctx(param):
        sync_fn(param, count, num_params)

The first branch handles a separate source of sharding, tensor parallelism. Without TP, GatheredParameters is active only for ZeRO-3; it reconstructs param inside the with block and returns it to sharded form afterward. The difference from verl is the interface, not the required operation: verl uses a DTensor method, while OpenRLHF uses a DeepSpeed context manager.

2. Releasing trainer memory during rollout

Weight sync makes the new actor available to rollout, but it does not remove the trainer's copy. In a colocated setup, the same GPUs may still hold FSDP parameter shards and Adam state while the rollout engine is trying to allocate serving weights, CUDA-graph buffers, and KV cache. Sharding reduces the trainer's footprint to roughly 1/S per rank; during rollout, even that smaller footprint may be unnecessary.

The source below implements the trainer-state offload shown in the second column, separately for model shards and optimizer state:

verl/utils/fsdp_utils.py· offload model and optimizer shards 
def offload_fsdp2_model_to_cpu(model, empty_cache=True):
    model.cpu()
    if empty_cache:
        get_torch_device().empty_cache()

def offload_fsdp_optimizer(optimizer):
    for param_group in optimizer.param_groups:
        for param in param_group["params"]:
            state = optimizer.state[param]
            for key, value in state.items():
                if isinstance(value, torch.Tensor):
                    state[key] = value.to("cpu", non_blocking=True)

model.cpu() moves the FSDP2 parameter shards; the optimizer loop moves tensor-valued state such as Adam moments. The corresponding load functions reverse these transfers before training resumes.

The interfaces a training script actually calls

The mechanisms above appear through a few different outer APIs. This is useful when reading an unfamiliar training stack: first identify how the model enters distributed training, then inspect the strategy and mesh passed through that interface.

PyTorch DDP and FSDP1 wrap a model. The constructor returns a new module-like object, and the training loop calls that wrapper in place of the original model. DDP replicates the model; FSDP1 can shard it according to sharding_strategy. Its auto_wrap_policy decides which submodules become separate FSDP units.

# Replicated data parallelism
model = DistributedDataParallel(model, device_ids=[local_rank])

# FSDP1
model = FullyShardedDataParallel(
    model,
    sharding_strategy=ShardingStrategy.FULL_SHARD,
    auto_wrap_policy=transformer_wrap_policy,
    device_mesh=mesh,
)

FSDP2 transforms modules in place. fully_shard() changes the selected module's parameters into sharded DTensors and installs the hooks that gather and reshard them. Calls are made from child modules toward the root, so each Transformer block can become its own communication unit.

for block in model.transformer_blocks:
    fully_shard(
        block,
        mesh=mesh,
        reshard_after_forward=True,
    )

fully_shard(model, mesh=mesh, reshard_after_forward=False)

The shape of mesh selects the placement. A one-dimensional mesh fully shards parameters across one group. A two-dimensional mesh replicates across one dimension and shards across the other, which gives FSDP2 its HSDP layout. HSDP therefore uses the same fully_shard() entry point; the mesh changes which ranks share and replicate each shard.

DeepSpeed ZeRO is selected when the training engine is initialized. The model, optimizer, and configuration enter deepspeed.initialize(); the zero_optimization.stage field chooses which state classes DeepSpeed partitions. The returned engine becomes the object used for forward, backward, and optimizer steps.

ds_config = {
    "zero_optimization": {
        "stage": 3,
    }
}

engine, optimizer, _, scheduler = deepspeed.initialize(
    model=model,
    optimizer=optimizer,
    config=ds_config,
)

outputs = engine(**batch)
loss = outputs.loss
engine.backward(loss)
engine.step()

How to read these interfaces. DistributedDataParallel(...) signals replicated parameters. FullyShardedDataParallel(...) signals FSDP1, with the strategy and wrapping policy in constructor arguments. fully_shard(...) signals FSDP2, with unit boundaries determined by which modules receive the call and placement determined by the mesh. deepspeed.initialize(...) moves the same decision into a DeepSpeed configuration, where the ZeRO stage is the first field to inspect.

FSDP and Megatron describe different layers of the distributed system. FSDP primarily decides how data-parallel training state is sharded and reconstructed. Megatron's TP, PP, CP, and EP decide how model computation and model structure are distributed. Modern stacks can compose these dimensions through device meshes, so the practical decision is no longer a strict choice between two mutually exclusive backbones. The useful questions are which dimension owns each parameter shard, which collective reconstructs it, and whether that collective matches the cluster topology and the RL phase schedule.
