The training backbone: Megatron-LM

By this point, the training object is visible: response tokens, masks, rewards or advantages, and policy logprobs have to line up before the actor loss is meaningful. The next question sits one layer lower. Once that object reaches the training engine, how is one actor update actually executed on a GPU cluster?

Megatron-LM is a good example for this layer because several RL infrastructure stacks use it directly as the training-side backend. Miles and slime wrap Megatron-style training workers around SGLang rollout, and verl can run its actor backend on Megatron as one of its supported training choices. It also exposes the central fact about this layer clearly, so we state it up front.

Megatron-LM is a reference training example built on Megatron Core. Megatron Core is the reusable layer: transformer building blocks, advanced parallelism strategies (TP, PP, DP, EP, and CP), mixed precision support (FP16, BF16, FP8, and FP4), and model architectures for custom training frameworks.

This quote tells us where to look. Megatron Core is the layer that owns the distributed training machinery: how the model is partitioned, how forward and backward are scheduled, how gradients are synchronized, and how the optimizer step is applied. RL infrastructure builds around that machinery. It supplies rollout data instead of ordinary pretraining text, computes an RL loss instead of next-token cross entropy, and then sends the updated actor back to the rollout side.

For someone already comfortable designing RL losses, this section is not mainly about the formula. It is about what happens after the formula enters a distributed training engine. Megatron decides which ranks see which slice of the batch, how large batches are broken into microbatches, when gradients are accumulated or synchronized, and which optimizer step actually creates the next policy version.

Background: the actor as a distributed object

A rank is one participating training process, usually associated with one GPU. A process group is a selected set of ranks that communicate for one purpose. Megatron builds several overlapping process groups because different parts of training need different communication patterns.

The algorithm can treat the actor as one policy πθ. The training engine has to represent that policy through many partial states: one rank may hold a shard of a weight matrix, another may hold a later range of layers, and another replica may work on a different slice of the batch. Megatron coordinates those partial states so the optimizer step still updates one logical actor.

The ways of splitting the work are named by what is being split:

  • Tensor parallelism (TP) splits tensors inside a layer — for example, different ranks hold different columns or rows of a weight matrix, and must communicate while computing one logical layer. Because this communication happens inside many layers, systems usually keep a TP group within one node, where GPUs can use fast links such as NVLinkNVLink is NVIDIA's high-bandwidth connection between GPUs inside the same server. It is much faster than sending tensor data through ordinary cross-machine networking, so it is a natural fit for tensor-parallel communication..
  • Pipeline parallelism (PP) splits the transformer by layers. Earlier layers live on one group of ranks, later layers on another, and activations move from stage to stage. The communication is sparse and can cross machines.
  • Data parallelism (DP) splits examples. Several ranks hold the same logical replica, each processes a different slice of the batch, and their gradients are synchronized before the optimizer step.
  • Expert parallelism (EP) splits MoE experts. Different ranks own different experts, so token routing becomes part of the distributed execution plan.
  • Context parallelism (CP) splits the sequence dimension itself across ranks, so one very long sequence can be processed by several GPUs at once.

These dimensions compose. A rank can be part of a TP group, a PP stage, and a DP replica at the same time. That is why "training on 128 GPUs" is not enough information. The important question is how those GPUs are grouped, because the grouping decides which parameters are local, which activations must be sent, and when gradients are synchronized.

Batch units: global batch, DP shard, microbatch

Once the actor is distributed, "the batch" is no longer a single object seen by one process. There are several batch units, and they matter for loss design:

  • Global batch. The full collection of training examples or tokens intended to contribute to one optimizer update.
  • Data-parallel shard. The slice of that global batch processed by one data-parallel replica.
  • Microbatch. A smaller chunk run through forward and backward because the full shard would not fit in memory at once.
  • Packed token batch. A tensor layout where several variable-length sequences may be concatenated, with metadata telling attention and loss code where sequence boundaries are.

With that vocabulary, one actor update reads as a sequence of execution phases:

RL batch with tokens, masks, rewards / advantages
  -> split into data-parallel shards and microbatches
  -> run distributed forward passes across the parallel dimensions
  -> compute token loss on the positions selected by the mask
  -> run backward passes and accumulate gradients
  -> synchronize the gradients that must agree across replicas
  -> optimizer step: theta changes

The word microbatch is the key one. A large RL batch may be too large to run in one forward/backward pass, so Megatron slices it into smaller pieces. Gradients from several microbatches can be accumulated before the optimizer step. During accumulation, the policy parameters have not changed. The actor becomes a new policy only when the optimizer step is applied.

Gradient accumulation. If a global batch is too large to fit on the GPUs at once, the trainer can run several smaller microbatches one after another. Each microbatch contributes gradients to the same parameter buffers. The optimizer does not step after every microbatch; it waits until the configured accumulation window is complete. This makes several small forward/backward passes behave like one larger batch update, up to details such as loss scaling, normalization, and numerical order.
