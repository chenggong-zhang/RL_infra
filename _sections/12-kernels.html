The layer beneath: CUDA, Triton, and TileLang

So far we have stayed at the RL infrastructure layer: how rollout, training, memory, cache, and weight sync are organized. This section goes one layer deeper. Those infrastructure choices eventually depend on GPU programs that implement attention, GEMM, normalization, softmax, and tensor movement. To understand why one rollout engine or training backend can be much faster than another, we need a basic map of the layer below PyTorch: CUDA, kernel libraries, and Python kernel DSLs such as Triton and TileLang.

A GPU mental model

At the lowest level, a computer manipulates bits through circuits. A bit is represented physically, for example by a voltage state that the circuit treats as 0 or 1. Logic gates combine those bit signals: an AND gate asks whether two inputs are both 1, an OR gate asks whether at least one is 1, and a NOT gate flips the signal. Larger circuits compose these small decisions into arithmetic units, registers, and control logic. Arithmetic units perform operations such as addition or multiplication. Registers are tiny, fast storage locations that hold values currently being used. Control logic decides which operation should run next and how data should move through the machine.

A processor is an organized machine for repeatedly reading instructions, moving values through registers and memory, and applying arithmetic units to those values. A GPU uses the same basic ingredients, but spends them differently. Instead of concentrating most resources into a few very flexible cores, it spreads many arithmetic units and registers across many parallel execution lanes, so the same kind of numeric operation can run on many pieces of data at once.

On NVIDIA GPUs, the repeated local compute units are called streaming multiprocessors, usually abbreviated as SMs. An SM has schedulers, registers, shared memory, and arithmetic units. A large GPU has many SMs, and each SM can keep many lightweight threads in flight.

CPU: strong control, limited parallel lanes

Good at: branching logic, operating-system work, scheduling, data loading, Python control flow, and irregular tasks where each step may do something different.

Weak at: applying the same numeric operation to millions of tensor elements. A CPU has powerful cores, but not enough parallel lanes to make large matrix and attention workloads cheap.

GPU: many lanes, weaker control

Good at: regular numeric workloads such as GEMM, attention, softmax, normalization, and batched tensor movement, where many lanes can run similar instructions on different data.

Weak at: highly irregular branching, small sequential tasks, and workloads that constantly move data without enough arithmetic reuse. A GPU is fast only when the work is shaped for it.

A program is a sequence of instructions that hardware can execute: load values, multiply or add them, compare conditions, store results, and move to the next instruction. At this level, the machine does not see "matrix multiplication" as a mathematical object. It sees a schedule of small steps through registers, arithmetic units, and memory. The role of code is to express the task in a human-writable form, then let compilers and runtimes lower it into such a program.

Now we can define kernel and thread. A GPU kernel is the GPU-side function body that the runtime launches over many parallel work items. Unlike an ordinary procedure call, a kernel is called, or launched, once and returns once, but it is executed many times: one execution per GPU thread. A GPU thread is one such execution instance of the kernel body. Each thread receives a logical position in the launched work: which CUDA block, or thread group, it belongs to and where it sits inside that block. The kernel code uses that position to decide which part of the data this thread is responsible for.

This is why GPU threads are lightweight. They are not like independent CPU threads running complicated unrelated tasks. They are many simple copies of the same program, spread over a large numeric index space: tensor elements, row fragments, tile positions, or token-related slots.

GPU threads are not scheduled one by one. They are scheduled in small groups called warps; on NVIDIA hardware, a warp is usually 32 threads. Think of a warp as a small team of threads moving together: the team usually follows one instruction stream, while each thread applies that instruction to its own data position (SIMT, single instruction, multiple threads).

CUDA: launching parallel work

CUDA is NVIDIA's GPU programming platform. It is not only a library, and it is not ordinary C. It includes several layers that work together:

CUDA C/C++ language extensions. CUDA adds GPU-specific syntax and built-ins to C/C++, such as __global__, threadIdx.x, blockIdx.x, and the launch syntax <<<...>>>.

CUDA compiler toolchain. The CUDA compiler, commonly nvcc, compiles CUDA C++ into host code that runs on the CPU and device code that runs on the GPU.

CUDA runtime and driver APIs. These APIs launch kernels, allocate GPU memory, copy data, manage streams and events, and synchronize work.

CUDA libraries. Libraries such as cuBLAS, cuDNN, NCCL, and CUTLASS provide highly optimized building blocks for linear algebra, neural-network kernels, communication, and tensor-core programming.

The simplest CUDA example is elementwise addition. The kernel body says what one GPU thread should do; the launch configuration says how many thread groups should be created:

__global__ void add_kernel(float* out, const float* a, const float* b, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        out[i] = a[i] + b[i];
    }
}

int block_size = 256;
int num_blocks = (n + block_size - 1) / block_size;
add_kernel<<<num_blocks, block_size>>>(out, a, b, n);

This tiny example contains the CUDA idea. add_kernel is written once, but the launch creates many GPU threads. threadIdx.x is the thread's position inside its CUDA block. blockIdx.x is the block's position inside the launched grid. blockDim.x is the number of threads in each block. Together they compute i, the data position owned by this thread. CUDA therefore gives the programmer a way to turn an indexed computation over an array into many parallel thread executions.

The launch syntax in the example, <<<num_blocks, block_size>>>, is CUDA's way of creating this structure. It creates a grid with num_blocks CUDA blocks. Each block contains block_size GPU threads. The hardware scheduler places blocks onto SMs. Threads inside the same block can cooperate through shared memory and block-level synchronization.

CUDA memory: where values live

CUDA does more than launch threads and blocks. It also defines how GPU memory is allocated, accessed, and synchronized. There are two levels to keep separate. At the API level, CUDA lets the program allocate GPU memory, copy data, share memory between processes, and synchronize work. At the kernel level, the question is more local: when a thread needs a value, where does that value live, and how many times will the kernel have to fetch it?

The important memory spaces are not equally fast. Registers are private to one thread and are the fastest place to keep values currently being used. Shared memory is visible to threads inside one CUDA block; it lets those threads cooperate on a tile of data. Global memory, usually HBM on modern accelerators, is much larger, but reading it repeatedly is expensive. Hardware caches such as L2 sit between global memory and the SMs, but a kernel writer still has to care about access patterns.

PyTorch on CUDA, and why CUDA Graphs exist

Most RL infrastructure code does not call CUDA kernels directly. It calls PyTorch. The CUDA connection appears when a PyTorch tensor is placed on a CUDA device:

x = torch.randn(4096, 4096, device="cuda")
w = torch.randn(4096, 4096, device="cuda")

y = x @ w
z = torch.softmax(y, dim=-1)

Putting a tensor on a CUDA device separates two things. The Python variable x is still a PyTorch object that the CPU-side Python program can hold, pass around, and inspect as metadata: shape, dtype, device, strides, and a pointer-like reference to storage. The numerical values of the tensor, however, live in GPU memory. So device="cuda" means the tensor's storage is allocated on a CUDA-capable GPU, not that Python itself is running on the GPU.

That is why the line y = x @ w does not multiply matrices in the Python interpreter. Python asks PyTorch to run a matrix multiply on CUDA tensors. PyTorch checks the tensor metadata, chooses an appropriate CUDA-backed implementation, often a vendor library such as cuBLAS or a generated kernel, and launches GPU work. The line torch.softmax(...) similarly becomes one or more GPU operations over buffers that live in GPU memory.

One detail is easy to miss: PyTorch CUDA calls are often asynchronous with respect to the CPU. The Python thread asks CUDA to do some GPU work, puts that work into a queue, and then may continue running before the GPU has finished. This is usually fine because later GPU operations in the same stream will wait in order. But if the CPU needs the result now, or if systems code is measuring time or reusing memory across components, it must explicitly wait:

y = x @ w                  # enqueue GPU work
z = torch.softmax(y, -1)   # enqueue more GPU work

torch.cuda.synchronize()   # wait until queued CUDA work is done

Now consider what happens when the same CUDA workload repeats. In ordinary PyTorch eager execution, every iteration still walks through the host-side path again: Python calls a PyTorch op, PyTorch dispatches the op, CUDA launches the needed kernels, and the driver submits those launches to the GPU. The GPU may be doing the same shape of work each time, but the CPU side still rebuilds the launch sequence each time.

CUDA Graphs are designed for that repeated-static case. If the operation pattern, tensor shapes, and memory addresses are stable, the system can capture the CUDA work once as a graph. Later iterations replay the captured graph instead of rediscovering and relaunching the same sequence from scratch. The computation is the same; the difference is that the launch path becomes cheaper and more predictable.

PyTorch CUDA semantics· CUDA Graphs and stream capture

Step 1: prepare the GPU memory that the graph will use. static_x and static_w are input buffers, and static_out is the output buffer. We save their addresses with data_ptr() only so we can later check that replay is using the same buffers, not newly allocated ones:

g = torch.cuda.CUDAGraph()

static_x = torch.empty((2, 2), device="cuda")
static_w = torch.empty((2, 2), device="cuda")
static_out = torch.empty((2, 2), device="cuda")

x_ptr = static_x.data_ptr()
w_ptr = static_w.data_ptr()

Step 2: capture the operation pattern once. This records GPU work that reads from static_x and static_w, then writes to static_out:

with torch.cuda.graph(g):
    torch.add(static_x, static_w, out=static_out)

After this capture, g contains the execution plan for this fixed CUDA work: read from the GPU memory address of static_x, read from the GPU memory address of static_w, run the add kernel, and write the result to the GPU memory address of static_out.

Step 3: replay the same captured work on new values. The contents change, but the storage addresses stay the same:

static_x.copy_(torch.ones((2, 2), device="cuda"))
static_w.copy_(2 * torch.ones((2, 2), device="cuda"))
g.replay()
print(static_x.data_ptr() == x_ptr, static_w.data_ptr() == w_ptr)
print(static_out.cpu())

static_x.copy_(10 * torch.ones((2, 2), device="cuda"))
static_w.copy_(20 * torch.ones((2, 2), device="cuda"))
g.replay()
print(static_x.data_ptr() == x_ptr, static_w.data_ptr() == w_ptr)
print(static_out.cpu())

CUDA from Python

The main lesson so far is that Python can touch CUDA at different depths. Most RL code stays at the PyTorch level: tensors live on CUDA devices, and PyTorch dispatches operations to CUDA kernels or vendor libraries. Sometimes, however, infrastructure code needs a lower-level CUDA handle: allocate memory directly, inspect devices, compile a kernel, use CUDA IPC, or coordinate communication.

NVIDIA/cuda-python is the Python entry point for that lower layer. The package is not one abstraction; it is a family of interfaces. cuda.bindings exposes low-level CUDA driver, runtime, NVRTC, and NVVM APIs. cuda.core gives a more Pythonic interface to CUDA runtime and JIT compilation. numba.cuda is a Python kernel DSL that compiles a restricted subset of Python to CUDA kernels. Newer interfaces such as cuda.tile and cuda.coop expose tile programming and block/warp cooperation patterns.

Triton: GPU kernels in Python

Triton is a Python-embedded language for writing GPU kernels. It does not replace CUDA as the underlying GPU platform. Instead, it replaces much of the CUDA C++ code a programmer would otherwise hand-write. The output is still GPU code; the input is a Python-shaped kernel body that the Triton compiler lowers to GPU execution.

The first idea to understand is block-level thinking. In the CUDA add_kernel above, the code computed one scalar index i, and one GPU thread owned that position. Triton raises the unit of reasoning. A Triton program instance owns a block, or tile, of positions. The programmer writes operations over vectors of offsets and values; by default, the compiler decides how that block-level work is mapped onto hardware threads.

This does not mean Triton automatically solves every performance problem. The programmer still chooses important tile shapes, memory layouts, masks, and sometimes autotuning configurations. The benefit is narrower and more practical: many custom tensor kernels can be written and revised inside a Python/PyTorch workflow, without building a CUDA C++ extension around every experiment. This is why Triton is common in research kernels and production inference stacks, often alongside CUDA C++, CUTLASS, and vendor libraries. The original MAPL 2019 paper frames the goal as higher productivity than CUDA while staying more flexible than fixed-function libraries.

The easiest way to see the difference is to write the same vector addition again, this time in Triton:

python/tutorials/01-vector-add.py· the canonical hello-world 
@triton.jit
def add_kernel(x_ptr,        # pointer to the first input vector
               y_ptr,        # pointer to the second input vector
               output_ptr,   # pointer to the output vector
               n_elements,   # total number of elements
               BLOCK_SIZE: tl.constexpr):
    pid = tl.program_id(axis=0)
    block_start = pid * BLOCK_SIZE
    offsets = block_start + tl.arange(0, BLOCK_SIZE)
    mask = offsets < n_elements
    x = tl.load(x_ptr + offsets, mask=mask)
    y = tl.load(y_ptr + offsets, mask=mask)
    output = x + y
    tl.store(output_ptr + offsets, output, mask=mask)

The important syntax is small. @triton.jit means the function body is compiled for the GPU, not executed by the Python interpreter. BLOCK_SIZE: tl.constexpr marks BLOCK_SIZE as a compile-time constant: the compiler knows the tile length while it builds the kernel, and it specializes the kernel around that length. tl.program_id(axis=0) identifies which program instance is running — on a first reading, think of it as a CUDA block id. tl.arange(0, BLOCK_SIZE) creates the vector of positions owned by this instance. tl.load and tl.store move a whole block of values under a mask. The missing thing is also important: there is no threadIdx. The Triton code names the tile of work, not the individual hardware thread that handles each element.

The launch is also plain Python, and it mirrors the CUDA launch syntax:

grid = (triton.cdiv(n_elements, BLOCK_SIZE),)   # number of program instances
add_kernel[grid](x, y, output, n_elements, BLOCK_SIZE=1024)

triton.cdiv is ceiling division — the same arithmetic as (n + block_size - 1) / block_size in the CUDA example. add_kernel[grid](...) is the Python counterpart of <<<num_blocks, block_size>>>, with one telling difference: the CUDA launch had to state both the number of blocks and the number of threads per block. The Triton launch only states how many program instances to create. By default, how many threads execute each instance is the compiler's business (it can be tuned with the num_warps option). One more practical detail: x, y, and output here are ordinary PyTorch tensors on a CUDA device. Triton accepts them directly and reads their GPU memory addresses — the same storage-on-GPU picture from the PyTorch subsection above.

TileLang: naming the memory spaces

TileLang is another Python-embedded language for GPU kernels, built on top of TVM. TVM is an open-source machine-learning compiler framework: it provides infrastructure for representing tensor programs, optimizing them, and generating code for different hardware backends. At the workflow level, TileLang resembles Triton: write a Python-shaped kernel, compile it, and call it on PyTorch CUDA tensors. The difference is what the language makes explicit.

Triton lets the programmer describe tile-level computation while leaving many placement choices to the compiler. TileLang exposes the memory choreography more directly. A kernel can name shared-memory buffers, register fragments, and explicit copies between memory spaces. This makes TileLang feel closer to a compact, Python-shaped version of hand-written CUDA: more control, but also more responsibility.

A small tiled matrix multiplication shows the style. Each program instance computes one tile of C = A·B. Tiles of A and B are copied from global memory into shared memory; the running output tile lives in a register fragment; the final result is copied back to global memory:

examples/quickstart.py· the canonical hello-world 
@tilelang.jit
def matmul(A, B, block_M: int, block_N: int, block_K: int):
    M, N, K = T.const("M, N, K")
    A: T.Tensor((M, K), T.float16)
    B: T.Tensor((K, N), T.float16)
    C = T.empty((M, N), T.float16)

    with T.Kernel(T.ceildiv(N, block_N), T.ceildiv(M, block_M), threads=128) as (bx, by):
        A_shared = T.alloc_shared((block_M, block_K), T.float16)
        B_shared = T.alloc_shared((block_K, block_N), T.float16)
        C_local  = T.alloc_fragment((block_M, block_N), T.float32)

        T.clear(C_local)                                      # zero the accumulator
        for ko in T.Pipelined(T.ceildiv(K, block_K), num_stages=3):
            T.copy(A[by * block_M, ko * block_K], A_shared)   # global -> shared
            T.copy(B[ko * block_K, bx * block_N], B_shared)   # global -> shared
            T.gemm(A_shared, B_shared, C_local)               # multiply into registers

        T.copy(C_local, C[by * block_M, bx * block_N])        # registers -> global
    return C

The code is useful because the memory spaces are visible. A_shared and B_shared are shared-memory staging buffers. C_local is a register fragment used as the accumulator. T.copy marks movement between memory spaces, and T.gemm updates the accumulator. The same blocked matrix multiplication idea could be implemented in CUDA or Triton, but TileLang writes the staging plan into the surface syntax.

Using the kernel is a two-step affair, and the second step should look familiar:

matmul_kernel = matmul.compile(M=1024, N=1024, K=1024,
                               block_M=128, block_N=128, block_K=32)
c = matmul_kernel(a, b)   # a, b: PyTorch tensors on a CUDA device

The compile step specializes the kernel to the chosen sizes, the way BLOCK_SIZE: tl.constexpr specialized the Triton kernel. The call itself takes PyTorch CUDA tensors directly, just as Triton did. TileLang also advertises compiler-side verification and portability features, including integration with Z3-based symbolic reasoning and backends beyond NVIDIA. For this survey, the simpler point is enough: TileLang is another route from Python to GPU kernels, with more explicit memory-space control than Triton.

Summary: a map, not a syntax course

The purpose of this section was not to teach CUDA, Triton, or TileLang syntax completely. It was to build a map of the layer below RL infrastructure: PyTorch tensors may store their data on CUDA devices; CUDA provides the execution and memory model for GPU work; CUDA Graphs record repeated GPU execution patterns; Triton and TileLang offer Python-shaped ways to write custom kernels above that lower layer.

If you want a systematic next step, start with Triton. Its tutorials, puzzles, and PyTorch integration make it the easiest kernel DSL to learn first. Read TileLang after that if you want a more explicit memory-space style or compiler-design ideas such as multi-backend lowering and symbolic verification. Use lower-level CUDA Python bindings when the problem is not "write a tensor kernel," but "control the CUDA runtime directly": driver APIs, IPC, device management, or specialized communication setup.
