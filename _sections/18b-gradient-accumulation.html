Case study — gradient accumulation and the meaning of one update

Gradient accumulation is easy to dismiss as a standard training trick: split a large batch into smaller microbatches, run backward several times, then call optimizer.step() once. In RL infrastructure, it deserves a separate look because "one update" is also the unit that controls weight sync, policy versioning, and how many rollout samples are consumed before the actor changes.

The cleanest entry point is slime's training configuration guide. It separates rollout production from training consumption. Rollout produces rollout_batch_size × n_samples_per_prompt samples. Training consumes global_batch_size × num_steps_per_rollout samples. The guide also makes a small but important distinction: a parameter update means the training-side optimizer.step(), not the later weight-sync call that copies the updated actor into the rollout engine.

slime/docs/zh/get_started/quick_start.md· rollout production and training consumption 
rollout_batch_size × n_samples_per_prompt
=
global_batch_size × num_steps_per_rollout

global_batch_size:
  the number of samples needed for one optimizer.step()

num_steps_per_rollout:
  how many optimizer steps are taken from the current rollout data

For a theorist, this is the first useful correction. The batch that appears in an algorithm is not necessarily the tensor batch that fits on one GPU forward/backward pass. global_batch_size is an algorithm-facing quantity: how much rollout data contributes to one actor update. micro_batch_size is a hardware-facing quantity: how much of that data the training engine can process at once without running out of memory.

slime's Megatron backend shows where the two meet. One rollout may contain several training steps, and each step has its own number of microbatches and its own effective global batch size:

slime/slime/backends/megatron_utils/model.py· each rollout can feed several optimizer steps 
num_steps_per_rollout = len(num_microbatches)

for step_id in range(num_steps_per_rollout):
    loss_dict, grad_norm = train_one_step(
        args,
        rollout_id,
        step_id,
        data_iterator,
        model,
        optimizer,
        opt_param_scheduler,
        num_microbatches[step_id],
        global_batch_sizes[step_id],
        microbatch_pbar=microbatch_pbar,
    )

The next function is the actual accumulation boundary. forward_backward_func runs forward/backward over num_microbatches microbatches. Gradients accumulate across those microbatches in the training model. Only after that does slime call optimizer.step(). Then it clears gradient buffers before the next optimizer step begins:

slime/slime/backends/megatron_utils/model.py· microbatches accumulate before optimizer.step 
return output_tensor, partial(
    loss_function,
    args,
    batch,
    num_microbatches,
    step_global_batch_size,
)

losses_reduced = forward_backward_func(
    forward_step_func=_wrap_forward_step_with_microbatch_pbar(
        forward_step, microbatch_pbar
    ),
    data_iterator=data_iterator,
    model=model,
    num_microbatches=num_microbatches,
    seq_length=args.seq_length,
    micro_batch_size=args.micro_batch_size,
    decoder_seq_length=args.decoder_seq_length,
    forward_only=False,
)

if valid_step:
    update_successful, grad_norm, num_zeros_in_grad = optimizer.step()
    assert update_successful
    opt_param_scheduler.step(increment=step_global_batch_size)

for model_chunk in model:
    model_chunk.zero_grad_buffer()
optimizer.zero_grad()

Read this as one optimizer update made from several smaller tensor passes. The microbatches are not independent RL updates. They are pieces of the same update until optimizer.step() happens. That is also why step_global_batch_size is passed into the loss and scheduler path: dynamic batching can change how many samples or tokens a step represents, and the framework has to keep learning-rate schedules and loss normalization tied to the effective update, not merely to the number of microbatch loops.

This boundary matters for the rest of the RL system. The rollout engine should not receive new actor weights after every microbatch backward. It should receive them after the optimizer has actually changed the training actor. A metric called "step" may mean microbatch progress, optimizer updates, rollout iterations, or weight-sync events depending on where it is logged. When reading a result, the safe question is: what exactly increments the policy version?

verl exposes the same distinction in a different style. Its performance guide says algorithmic quantities such as train batch size and PPO mini-batch size are global, while *micro_batch_size_per_gpu is a local performance parameter. It even suggests larger microbatches for forward-only work such as reference logprobs than for actor PPO training, because forward-only paths do not store the same backward activations.

verl/docs/perf/perf_tuning.rst· global algorithmic batch vs per-GPU microbatch

Gradient accumulation is the mechanism that lets the algorithm speak in global update units while the engine executes memory-sized pieces. In RL infrastructure, the distinction protects three invariants: the loss should be normalized over the intended update batch, the optimizer should step only after all pieces of that update have contributed gradients, and rollout weight sync should happen after the actor truly changed.
