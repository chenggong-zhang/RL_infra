FlashAttention: basic tutorial of Triton

This section uses Stanford CS336 lecture 6 and CS336 Assignment 2: Systems and Parallelism as the learning path. The concrete target is the assignment's FlashAttention-2 task: replace a PyTorch attention implementation with a Triton kernel, add causal masking, implement backward, and benchmark the result.

The order matters. We should not start from attention. First we need enough Triton literacy to read a kernel: what a program instance is, how a launch grid divides work, how pointers and strides describe tensors, how masks protect boundary loads, how block pointers describe rectangular tiles, and how a Triton kernel is wrapped back into PyTorch autograd. Only after those pieces are in place does FlashAttention become readable.

Part I. Triton from zero

Triton is a Python-embedded language for GPU kernels. The kernel body is written in Python-like syntax, but a function marked with @triton.jit is compiled into GPU code. It is called from Python, usually with PyTorch tensors as inputs, but the actual work happens on the GPU.

The simplest way to place Triton in the stack is this:

PyTorch gives you tensor objects and high-level operations such as x @ y. CUDA is NVIDIA's underlying GPU programming/runtime platform. Triton lets you write custom GPU kernels from Python, while still lowering to GPU execution through the CUDA/NVIDIA stack.

For this section, the key idea is tile-level programming. In ordinary Python, you may write a loop over individual elements. In CUDA C++, you often think about individual GPU threads. In Triton, the first useful mental unit is a program instance: one launched copy of the kernel that owns a block, or tile, of tensor positions.

Program instances and launch grids

A Triton kernel is launched with a grid:

add_kernel[(num_programs,)](x, y, out, n_elements, BLOCK=1024)

This means: create num_programs program instances. Inside the kernel, each instance can ask for its own id:

pid = tl.program_id(0)

If BLOCK = 1024, then program instance pid = 0 can handle elements 0..1023, pid = 1 can handle 1024..2047, and so on. This is the first Triton reading skill: tl.program_id usually tells you which tile this program instance owns.

A first Triton kernel

Here is vector addition, written in the style of the official Triton tutorial:

@triton.jit
def add_kernel(x_ptr, y_ptr, out_ptr, n_elements, BLOCK: tl.constexpr):
    pid = tl.program_id(0)
    offsets = pid * BLOCK + tl.arange(0, BLOCK)
    mask = offsets < n_elements

    x = tl.load(x_ptr + offsets, mask=mask)
    y = tl.load(y_ptr + offsets, mask=mask)
    tl.store(out_ptr + offsets, x + y, mask=mask)

Read it line by line. x_ptr, y_ptr, and out_ptr are pointers to GPU memory. BLOCK: tl.constexpr means BLOCK is known at compile time, so Triton can specialize the kernel for that tile size. tl.arange(0, BLOCK) creates a vector of offsets inside the tile. mask handles the last tile when the vector length is not divisible by BLOCK. tl.load reads many positions at once, and tl.store writes many positions at once.

This is the basic Triton pattern:

program id -> tile offsets -> boundary mask -> load tile -> compute -> store tile

Why pointers and strides appear

PyTorch tensors carry metadata: shape, dtype, device, and strides. A stride tells how far you move in memory when an index increases by one along a dimension. Triton kernels often receive raw pointers plus stride values because the kernel must compute addresses explicitly.

For a 2D tensor X, the logical element X[row, col] lives at:

X_ptr + row * stride_row + col * stride_col

If the tensor is contiguous in row-major order, stride_col is usually 1 and stride_row is the width of the row. If the tensor is transposed or sliced, the strides can be different. This is why a correct Triton kernel is partly a memory-layout program. It does not only know the formula; it knows how to find the values.

Two-dimensional tiles

Once the reader understands one-dimensional offsets, the two-dimensional version is natural. A program instance may own a rectangular tile:

rows = row_start + tl.arange(0, BLOCK_M)
cols = col_start + tl.arange(0, BLOCK_N)
offsets = rows[:, None] * stride_m + cols[None, :] * stride_n

The notation rows[:, None] turns row offsets into a column vector; cols[None, :] turns column offsets into a row vector. Together they form a BLOCK_M x BLOCK_N matrix of addresses. This pattern appears everywhere in tiled kernels: matrix multiply, attention, normalization, and loss kernels.

Block pointers

The CS336 assignment uses Triton's block pointer abstraction, tl.make_block_ptr, because FlashAttention loads rectangular tiles from Q, K, V, and writes rectangular tiles to O. A block pointer packages the pointer arithmetic into one object:

Q_block_ptr = tl.make_block_ptr(
    Q_ptr + batch_index * stride_qb,
    shape=(N_QUERIES, D),
    strides=(stride_qq, stride_qd),
    offsets=(query_tile_index * Q_TILE_SIZE, 0),
    block_shape=(Q_TILE_SIZE, D),
    order=(1, 0),
)

Read the fields this way:

  • Q_ptr + batch_index * stride_qb: start at the current batch element.
  • shape=(N_QUERIES, D): the logical matrix seen by this batch element.
  • strides=(stride_qq, stride_qd): how to move along query positions and feature positions.
  • offsets=(query_tile_index * Q_TILE_SIZE, 0): where this tile starts.
  • block_shape=(Q_TILE_SIZE, D): the tile size to load.
  • order=(1, 0): the memory-order hint Triton uses for efficient loading.

After creating a block pointer, the kernel can load the whole tile:

Q_tile = tl.load(Q_block_ptr, boundary_check=(0, 1), padding_option="zero")

That line says: load a Q_TILE_SIZE x D tile, and if the tile crosses the tensor boundary, pad invalid entries with zero. For the assignment, many test shapes are powers of two, but real kernels still need boundary logic.

Matrix multiply inside a kernel

Triton provides tl.dot for tile matrix multiplication. If Q_tile has shape Bq x D and K_tile has shape Bk x D, the attention score tile is:

S = tl.dot(Q_tile, tl.trans(K_tile)) * scale

This is still small tile arithmetic. The full attention matrix is never created. Each program instance creates one score tile at a time, uses it, then moves on.

For accumulation, use float32 unless you have a careful reason not to:

acc = tl.zeros((Q_TILE_SIZE, D), dtype=tl.float32)

This matters because attention combines exponentials, reductions, and matrix multiplies. The inputs may be BF16 or FP16, but running maxima, denominators, and accumulators are usually kept in FP32 for stability.

Wrapping Triton back into PyTorch

A Triton kernel by itself is not enough for a PyTorch model. PyTorch's autograd system needs a Python object that says how to run forward and backward. The assignment uses torch.autograd.Function:

class MyOp(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x):
        y = torch.empty_like(x)
        my_kernel[(grid,)](x, y, ...)
        ctx.save_for_backward(x, y)
        return y

    @staticmethod
    def backward(ctx, dy):
        x, y = ctx.saved_tensors
        dx = my_backward(x, y, dy)
        return dx

For FlashAttention, the forward will save Q, K, V, O, and L. It will not save the full attention probability matrix. That design choice will make sense once we introduce attention.

Part II. Attention after Triton

Now we have the needed Triton pieces: program instances, launch grids, offsets, masks, strides, block pointers, tl.dot, accumulators, and autograd wrapping. We can finally ask what FlashAttention is optimizing.

For one batch/head, ordinary attention is:

S = QK^T / sqrt(d)
P = softmax(mask(S))
O = PV

In naive PyTorch attention, S and P are materialized as tensors. If the sequence length is N, each has shape N x N per batch/head. At long context length, this becomes the memory wall. At N = 32768, the attention matrix has more than one billion entries per head. Backward makes this worse because ordinary formulas also want the probability matrix P.

FlashAttention keeps the mathematical result exact while changing the memory schedule. It computes attention in tiles, keeps temporary score/probability tiles on chip, and writes only the final output O plus a compact row-wise statistic L.

The four ideas behind FlashAttention

The assignment names tiling, recomputation, and operator fusion; online softmax is the mechanism that makes tiled softmax possible.

  • Tiling. Handle one block of query rows and stream over key/value blocks. A small score tile exists temporarily inside the kernel.
  • Online softmax. Keep a running row maximum m and denominator proxy l, so softmax can be accumulated over key tiles without seeing the full row at once.
  • Recomputation. Save L = logsumexp(S) instead of saving P. Backward recomputes local probability tiles from Q, K, and L.
  • Fusion. Combine score computation, softmax update, and multiplication by V in one kernel so intermediate tiles are not written to HBM between PyTorch operations.

Step 1. Write a tiled PyTorch reference

The first concrete answer is not Triton. Write a slow PyTorch version that follows the FlashAttention loop. It gives you a trusted reference for O and L before pointer arithmetic enters.

def flash_forward_tiled_pytorch(Q, K, V, is_causal=False, Bq=16, Bk=16):
    # Q, K, V: [batch, seq, d]
    batch, Nq, d = Q.shape
    Nk = K.shape[1]
    scale = d ** -0.5

    O = torch.empty_like(Q)
    L = torch.empty((batch, Nq), device=Q.device, dtype=torch.float32)

    for b in range(batch):
        for q0 in range(0, Nq, Bq):
            q1 = min(q0 + Bq, Nq)
            Qi = Q[b, q0:q1].float()

            Oi = torch.zeros((q1 - q0, d), device=Q.device, dtype=torch.float32)
            m = torch.full((q1 - q0,), -float("inf"), device=Q.device)
            l = torch.zeros((q1 - q0,), device=Q.device)

            q_idx = torch.arange(q0, q1, device=Q.device)
            for k0 in range(0, Nk, Bk):
                k1 = min(k0 + Bk, Nk)
                Kj = K[b, k0:k1].float()
                Vj = V[b, k0:k1].float()

                S = Qi @ Kj.T * scale
                if is_causal:
                    k_idx = torch.arange(k0, k1, device=Q.device)
                    S = S.masked_fill(q_idx[:, None] < k_idx[None, :], -1e6)

                m_new = torch.maximum(m, S.max(dim=1).values)
                P_tilde = torch.exp(S - m_new[:, None])
                alpha = torch.exp(m - m_new)
                l_new = alpha * l + P_tilde.sum(dim=1)
                Oi = alpha[:, None] * Oi + P_tilde @ Vj
                m, l = m_new, l_new

            O[b, q0:q1] = (Oi / l[:, None]).to(Q.dtype)
            L[b, q0:q1] = m + torch.log(l)

    return O, L

This code is the algorithm in executable form. The output accumulator Oi, running max m, and running denominator l are per query row. The loop over Kj,Vj streams across key/value tiles. The full N x N score matrix is never allocated.

Verification at this step should compare against ordinary PyTorch attention at small sizes:

def attention_reference(Q, K, V, is_causal=False):
    d = Q.shape[-1]
    S = Q @ K.transpose(-1, -2) / math.sqrt(d)
    if is_causal:
        Nq, Nk = Q.shape[-2], K.shape[-2]
        q = torch.arange(Nq, device=Q.device)
        k = torch.arange(Nk, device=Q.device)
        S = S.masked_fill(q[None, :, None] < k[None, None, :], -1e6)
    P = torch.softmax(S, dim=-1)
    return P @ V, torch.logsumexp(S.float(), dim=-1)

The assignment's first milestone, test_flash_forward_pass_pytorch, is exactly this stage: make the tiled algorithm correct before making it fast.

Step 2. Translate the reference into a Triton forward kernel

Now map the same loop to Triton. The launch grid is (Tq, batch_size): one program instance owns one query tile for one batch item.

# Python-side launch
Tq = triton.cdiv(N_QUERIES, Q_TILE_SIZE)
grid = (Tq, batch_size)

flash_fwd_kernel[grid](
    Q, K, V, O, L,
    Q.stride(0), Q.stride(1), Q.stride(2),
    K.stride(0), K.stride(1), K.stride(2),
    V.stride(0), V.stride(1), V.stride(2),
    O.stride(0), O.stride(1), O.stride(2),
    L.stride(0), L.stride(1),
    N_QUERIES: tl.constexpr,
    N_KEYS: tl.constexpr,
    scale,
    D=d, Q_TILE_SIZE=64, K_TILE_SIZE=64,
    is_causal=is_causal,
)

The kernel skeleton mirrors the PyTorch reference. This is the shape to fill in:

@triton.jit
def flash_fwd_kernel(
    Q_ptr, K_ptr, V_ptr, O_ptr, L_ptr,
    stride_qb, stride_qq, stride_qd,
    stride_kb, stride_kk, stride_kd,
    stride_vb, stride_vk, stride_vd,
    stride_ob, stride_oq, stride_od,
    stride_lb, stride_lq,
    N_QUERIES, N_KEYS, scale,
    D: tl.constexpr,
    Q_TILE_SIZE: tl.constexpr,
    K_TILE_SIZE: tl.constexpr,
    is_causal: tl.constexpr,
):
    query_tile_index = tl.program_id(0)
    batch_index = tl.program_id(1)

    Q_block = tl.make_block_ptr(
        Q_ptr + batch_index * stride_qb,
        shape=(N_QUERIES, D),
        strides=(stride_qq, stride_qd),
        offsets=(query_tile_index * Q_TILE_SIZE, 0),
        block_shape=(Q_TILE_SIZE, D),
        order=(1, 0),
    )
    O_block = tl.make_block_ptr(
        O_ptr + batch_index * stride_ob,
        shape=(N_QUERIES, D),
        strides=(stride_oq, stride_od),
        offsets=(query_tile_index * Q_TILE_SIZE, 0),
        block_shape=(Q_TILE_SIZE, D),
        order=(1, 0),
    )
    L_block = tl.make_block_ptr(
        L_ptr + batch_index * stride_lb,
        shape=(N_QUERIES,),
        strides=(stride_lq,),
        offsets=(query_tile_index * Q_TILE_SIZE,),
        block_shape=(Q_TILE_SIZE,),
        order=(0,),
    )

    Qi = tl.load(Q_block, boundary_check=(0, 1), padding_option="zero")
    Oi = tl.zeros((Q_TILE_SIZE, D), dtype=tl.float32)
    m = tl.full((Q_TILE_SIZE,), -float("inf"), dtype=tl.float32)
    l = tl.zeros((Q_TILE_SIZE,), dtype=tl.float32)

    q_offsets = query_tile_index * Q_TILE_SIZE + tl.arange(0, Q_TILE_SIZE)

    for k0 in range(0, N_KEYS, K_TILE_SIZE):
        K_block = tl.make_block_ptr(
            K_ptr + batch_index * stride_kb,
            shape=(N_KEYS, D),
            strides=(stride_kk, stride_kd),
            offsets=(k0, 0),
            block_shape=(K_TILE_SIZE, D),
            order=(1, 0),
        )
        V_block = tl.make_block_ptr(
            V_ptr + batch_index * stride_vb,
            shape=(N_KEYS, D),
            strides=(stride_vk, stride_vd),
            offsets=(k0, 0),
            block_shape=(K_TILE_SIZE, D),
            order=(1, 0),
        )

        Kj = tl.load(K_block, boundary_check=(0, 1), padding_option="zero")
        Vj = tl.load(V_block, boundary_check=(0, 1), padding_option="zero")

        S = tl.dot(Qi, tl.trans(Kj)) * scale

        k_offsets = k0 + tl.arange(0, K_TILE_SIZE)
        valid_k = k_offsets < N_KEYS
        S = tl.where(valid_k[None, :], S, -1.0e6)
        if is_causal:
            S = tl.where(q_offsets[:, None] >= k_offsets[None, :], S, -1.0e6)

        m_new = tl.maximum(m, tl.max(S, axis=1))
        P_tilde = tl.exp(S - m_new[:, None])
        alpha = tl.exp(m - m_new)
        l_new = alpha * l + tl.sum(P_tilde, axis=1)
        Oi = alpha[:, None] * Oi + tl.dot(P_tilde.to(Vj.dtype), Vj)
        m = m_new
        l = l_new

    Oi = Oi / l[:, None]
    L = m + tl.log(l)

    tl.store(O_block, Oi.to(O_block.type.element_ty), boundary_check=(0, 1))
    tl.store(L_block, L, boundary_check=(0,))

This is not just pseudocode. It is the complete control structure the assignment wants. In this teaching version, N_QUERIES and N_KEYS are marked as tl.constexpr because the loop over key tiles should be known when Triton compiles the kernel. You may still adjust exact tile sizes and signatures to match your adapter, but the algorithmic content is fixed: one query tile, loop over key/value tiles, online-softmax update, store O and L.

Step 3. Wrap the Triton forward in autograd.Function

The Python wrapper allocates outputs, launches the kernel, saves what backward needs, and returns only O:

class FlashAttentionTriton(torch.autograd.Function):
    @staticmethod
    def forward(ctx, Q, K, V, is_causal=False):
        batch, Nq, d = Q.shape
        Nk = K.shape[1]
        O = torch.empty_like(Q)
        L = torch.empty((batch, Nq), device=Q.device, dtype=torch.float32)

        Q_TILE_SIZE = 64
        K_TILE_SIZE = 64
        grid = (triton.cdiv(Nq, Q_TILE_SIZE), batch)

        flash_fwd_kernel[grid](
            Q, K, V, O, L,
            Q.stride(0), Q.stride(1), Q.stride(2),
            K.stride(0), K.stride(1), K.stride(2),
            V.stride(0), V.stride(1), V.stride(2),
            O.stride(0), O.stride(1), O.stride(2),
            L.stride(0), L.stride(1),
            Nq, Nk, d ** -0.5,
            D=d,
            Q_TILE_SIZE=Q_TILE_SIZE,
            K_TILE_SIZE=K_TILE_SIZE,
            is_causal=is_causal,
        )

        ctx.save_for_backward(Q, K, V, O, L)
        ctx.is_causal = is_causal
        return O

    @staticmethod
    def backward(ctx, dO):
        Q, K, V, O, L = ctx.saved_tensors
        dQ, dK, dV = flash_backward_pytorch(Q, K, V, O, dO, L, ctx.is_causal)
        return dQ, dK, dV, None

For the forward-only test, the backward can temporarily raise NotImplementedError. Once the forward passes, replace it with the PyTorch backward below.

Step 4. Add causal masking correctly

Causal masking belongs inside the score-tile update, before softmax. The rule is simple: query row q can see key column k only when k <= q.

q_offsets = query_tile_index * Q_TILE_SIZE + tl.arange(0, Q_TILE_SIZE)
k_offsets = k0 + tl.arange(0, K_TILE_SIZE)
causal_mask = q_offsets[:, None] >= k_offsets[None, :]
S = tl.where(causal_mask, S, -1.0e6)

Also keep the non-causal boundary mask for k_offsets < N_KEYS. Causal masking removes future positions; boundary masking removes positions outside the actual sequence length. They solve different problems.

Step 5. Implement backward with recomputation

The assignment first asks for backward in PyTorch, optionally compiled. The computation uses L saved from forward, so it does not need the stored attention matrix:

S = QK^T / sqrt(d)
P = exp(S - L)
D = rowsum(O * dO)
dP = dO V^T
dS = P * (dP - D)
dQ = dS K / sqrt(d), dK = dS^T Q / sqrt(d), dV = P^T dO
@torch.compile
def flash_backward_pytorch(Q, K, V, O, dO, L, is_causal=False):
    d = Q.shape[-1]
    scale = d ** -0.5

    S = Q.float() @ K.float().transpose(-1, -2) * scale
    if is_causal:
        Nq, Nk = Q.shape[-2], K.shape[-2]
        q = torch.arange(Nq, device=Q.device)
        k = torch.arange(Nk, device=Q.device)
        S = S.masked_fill(q[None, :, None] < k[None, None, :], -1e6)

    P = torch.exp(S - L[:, :, None])
    D = (O.float() * dO.float()).sum(dim=-1)
    dP = dO.float() @ V.float().transpose(-1, -2)
    dS = P * (dP - D[:, :, None])

    dQ = dS @ K.float() * scale
    dK = dS.transpose(-1, -2) @ Q.float() * scale
    dV = P.transpose(-1, -2) @ dO.float()
    return dQ.to(Q.dtype), dK.to(K.dtype), dV.to(V.dtype)

This backward is not memory-optimal for very long sequences because it materializes S and P again, but it is a good correctness bridge. It lets the assignment test the custom forward with real gradients before you write a tiled Triton backward.

Step 6. Understand the optional Triton backward

The optional backward is not a mystery; it is the same formulas tiled. The trick is work partitioning. One pass loops over key tiles and accumulates dK and dV. Another pass loops over query tiles and accumulates dQ. That means P is recomputed twice.

# pass A: one program owns a K/V tile
for each K_j, V_j:
    dK_j = 0
    dV_j = 0
    for each Q_i:
        recompute S_ij and P_ij from Q_i, K_j, L_i
        dV_j += P_ij.T @ dO_i
        dS_ij = P_ij * (dO_i @ V_j.T - D_i)
        dK_j += dS_ij.T @ Q_i * scale
    store dK_j, dV_j

# pass B: one program owns a Q tile
for each Q_i:
    dQ_i = 0
    for each K_j, V_j:
        recompute S_ij and P_ij
        dS_ij = P_ij * (dO_i @ V_j.T - D_i)
        dQ_i += dS_ij @ K_j * scale
    store dQ_i

Why compute P twice? Because avoiding atomics can be worth more than avoiding extra matmul/exp work. If many program instances tried to update the same gradient tile, they would need slow coordination. Two organized passes give each output tile a clear owner.

Step 7. Benchmark the result

Use triton.testing.do_bench, not naive wall-clock timing, and warm up before measuring. A minimal benchmark has this shape:

def bench_flash(batch=1, N=4096, d=64, dtype=torch.bfloat16, causal=True):
    Q = torch.randn(batch, N, d, device="cuda", dtype=dtype, requires_grad=True)
    K = torch.randn(batch, N, d, device="cuda", dtype=dtype, requires_grad=True)
    V = torch.randn(batch, N, d, device="cuda", dtype=dtype, requires_grad=True)

    def forward_only():
        return FlashAttentionTriton.apply(Q, K, V, causal)

    def forward_backward():
        O = FlashAttentionTriton.apply(Q, K, V, causal)
        loss = O.float().sum()
        loss.backward()
        Q.grad = K.grad = V.grad = None

    fwd_ms = triton.testing.do_bench(forward_only)
    bwd_ms = triton.testing.do_bench(forward_backward)
    return fwd_ms, bwd_ms

The assignment sweep uses sequence lengths up to 65536, head dimensions up to 128, BF16 and FP32, batch size 1, and causal masking. For a blog reader, the important observation is how the curves change with N. Naive attention eventually fails because of the N x N matrix. FlashAttention should keep running much longer because it never stores that matrix.

Step 8. Optimize after correctness

Once the tests pass, optimize in this order:

  • Tile sizes. Tune Q_TILE_SIZE and K_TILE_SIZE. Bigger tiles improve reuse but use more registers and on-chip resources; smaller tiles may launch too much work.
  • Causal early exit. Skip key tiles that are guaranteed to be fully masked.
  • Diagonal separation. Compute fully visible tiles without index comparisons; use square masking only on diagonal tiles.
  • Triton backward. Use two organized passes to avoid atomics: one for dK/dV, one for dQ.
  • Autotuning budget. Triton autotune can find better tile shapes, but too many candidates can make first-run compilation too slow.
  • TMA on newer GPUs. Tensor Memory Accelerator can move tiles efficiently on supported architectures, but it belongs after the basic kernel is correct.

The clean mental model is: first remove the N x N HBM object, then improve the tile schedule. FlashAttention's main win comes from IO awareness. The later wins come from reducing wasted tile work, avoiding atomics, choosing hardware-friendly tile shapes, and lowering launch overhead.

Why this matters for RL infrastructure

At the framework level, attention looks like one operator inside rollout or training. At the systems level, the implementation decides whether long-context rollout is feasible. If the kernel materializes the attention matrix, memory grows quadratically in sequence length. If the kernel streams tiles and saves only compact summaries, much longer prompts and trajectories fit.

This connects directly to earlier sections. RadixAttention reduces repeated prefill by reusing cached prefixes. FlashAttention reduces the cost of computing attention over the tokens that still must be processed. Memory choreography makes room for inference and training phases. Triton is one of the languages engineers use when PyTorch-level composition cannot express the memory schedule they need.
